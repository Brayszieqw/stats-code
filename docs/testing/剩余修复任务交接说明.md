## 1. ✅ 相关/t 检验报告不完整（已完成，仅供复核）

### 症状（真机证据）

`chrome-acceptance-report.json` 里三条 `PASS_WITH_UI_GAP`：

- `correlation-pearson`：`"Report omitted r and CI and rendered no chart."`
- `correlation-spearman`：同上（omitted rho and CI）
- `ttest-welch`：`"Report omitted t, df, mean difference, and confidence interval."`

引擎数值全对（Pearson r 与 NIST 参考值到 1e-16 一致），**纯 UI 缺渲染分支**。

### 根因

`web/src/components/ThreeLineTable.tsx` 的分派器只认三种载荷：
Table One（`payload.groups[0].continuous`）、回归系数（`payload.coefficients`）、
ANOVA（`algorithm_id === 'anova'`）。t 检验和相关分析的扁平载荷
（`r` / `t_statistic` / `ci_lower` 直接挂在 payload 顶层）落到函数末尾 `return null`，
于是 `ReportViewer` 只渲染出一个空壳 + 指标卡里的 p 与 n。

同时 `ReportViewer.tsx` 的指标卡只从 `coefficients` 取效应量与置信区间，
扁平载荷没有 `coefficients`，效应量卡与 CI 卡整块消失。

### 我做的改动

**`web/src/components/ThreeLineTable.tsx`**
- 新增 `renderTtest(payload)`：组均值（带每组 n）→ 均值差 → 置信区间 → t → df → p。
  CI 标签按 `payload.alpha` 动态算（α=0.01 显示「99% 置信区间」）。
- 新增 `renderCorrelation(payload)`：系数（Pearson r / Spearman ρ 按 method 区分标签）
  → CI → R²（**仅 Pearson**，因为 Spearman 的 ρ² 不是可解释方差比例）→ t → df → p → n。
- 新增 `renderPower(payload)`：每组样本量、两组合计、实际功效、效应量、α。
- 分派器加三个判据：
  - t 检验：`algorithm_id === 'ttest' && typeof payload.t_statistic === 'number'`
  - 相关：`algorithm_id === 'correlation' && typeof payload.r === 'number'`
  - 功效：`typeof payload.required_n === 'number' && typeof payload.achieved_power === 'number'`
    （**不能用 algorithm_id**，因为 `skillToAlgorithm('power')` 按设计返回 `null`）

**`web/src/views/pro/ReportViewer.tsx`**
- 加 `flatEffect`：按算法给扁平载荷的效应量配语义标签
  （t 检验→「均值差」、相关→「Pearson r」/「Spearman ρ」、ANOVA→「F 统计量」），
  而不是笼统写「Beta」。
- `confidenceInterval` 回退到 `payload.ci_lower/ci_upper`。
- `tableTitle` / `hasRenderableTable` 补上三种新类型。
- 功效分析的样本量卡改成显示 `required_n`（向上取整）而不是数据集行数，
  文案「每组样本量 / 达到目标功效所需」。

## 3. ❌ 历史工件绑定错乱（点旧报告显示最新运行）

**这是三个未开工项里最复杂、也最重要的一个**（涉及科研可信性：
用户以为在看第 1 次分析，其实看的是第 3 次的数字）。

### 症状（真机证据）

`chrome-acceptance-report.json` 的 `uiDefects[0]`：
```
"Historical report selection can remain bound to the latest run."
```

复现步骤：
1. 专业模式，同一会话里连续跑 3 次不同分析（比如 t 检验 → 相关 → ANOVA）。
2. 聊天流里会有 3 个「分析工件已更新」气泡，每个都带自己的 run_id 前 8 位。
3. 点**第 1 个**气泡的「查看报告」。
4. 右侧检查器打开报告视图，显示的是**第 3 次（ANOVA）**的结果，
   头部 run_id 也是第 3 次的。

### 根因（一句话：点击事件丢掉了「是哪一次运行」这个信息）

链路如下，逐个文件：

**a) 气泡按钮不传 run 标识。**
`web/src/components/MessageList.tsx:249-274`，`AnalysisResultReference` 的三个按钮：
```tsx
onClick={() => onOpenResult?.('report')}   // ← 只传视图名
```
虽然组件内部有 `result`（就是那条消息自己的 SkillResult），却没往上传。

**b) 回调签名里没有 run 的位置。**
`MessageList.tsx:48`、`views/pro/AssistantPanel.tsx:36`：
```ts
onOpenResult?: (view: 'report' | 'chart' | 'code') => void;
```

**c) 处理函数只切视图。**
`web/src/views/ProModeView.tsx:371-374`：
```tsx
const handleOpenResult = (view: 'report' | 'chart' | 'code') => {
  setWorkspaceView(view);
  setWorkspaceOpen(true);
};
```

**d) 检查器的内容压根不看点击，只看「最后一条」。**
`ProModeView.tsx:203`：
```tsx
const { result } = useLatestAnalysis(workspaceMessages);
```
`useLatestAnalysis`（`web/src/hooks/useLatestAnalysis.ts:28-38`）从数组**尾部往前**
找第一条带 `skillResult` 的 agent 消息。所以它永远返回最新的那次。

`ReportViewer` 同理：`views/pro/ReportViewer.tsx` 接的是 `messages` 全量数组，
内部自己再取 latest。**点哪个气泡都不影响它。**

### 精确改法（4 处文件，按顺序改）

#### 3.1 `web/src/views/ProModeView.tsx` — 加「被选中的 run」状态

在 `const { result } = useLatestAnalysis(workspaceMessages);` 附近改成：

```tsx
/**
 * 用户从聊天流里点选的历史运行 id。null = 跟随最新运行。
 *
 * 检查器过去只由 useLatestAnalysis 驱动，点历史气泡只切视图不换内容，
 * 用户会把第 3 次的数字读成第 1 次的（真机审计缺陷：Historical report
 * selection can remain bound to the latest run）。科研场景里这属于
 * 数据串台，必须让选择显式化。
 */
const [selectedRunId, setSelectedRunId] = useState<string | null>(null);

const { result: latestResult } = useLatestAnalysis(workspaceMessages);

/** 被点选的那条运行；找不到（会话切换/消息被清）时安全回退到最新。 */
const selectedResult = useMemo(() => {
  if (!selectedRunId) return null;
  for (let i = workspaceMessages.length - 1; i >= 0; i -= 1) {
    const candidate = workspaceMessages[i];
    if (candidate?.skillResult?.analysis?.run_id === selectedRunId) {
      return candidate.skillResult;
    }
  }
  return null;
}, [selectedRunId, workspaceMessages]);

const result = selectedResult ?? latestResult;
/** 是否正在看历史（而不是最新）——用于顶部提示条。 */
const isViewingHistorical = Boolean(
  selectedResult
  && latestResult?.analysis?.run_id
  && selectedResult.analysis?.run_id !== latestResult.analysis.run_id,
);
```

> `analysis` 那一行（`const analysis = result?.analysis ?? null;`）不用动，
> 它会自动跟着新的 `result` 走，`analysisDataset` 也随之正确。

#### 3.2 同文件 — `handleOpenResult` 接受 run id

```tsx
const handleOpenResult = (view: 'report' | 'chart' | 'code', runId?: string) => {
  // 显式点选历史运行时锁定它；点最新那条（或拿不到 id）时回到跟随模式。
  setSelectedRunId(runId && runId !== latestResult?.analysis?.run_id ? runId : null);
  setWorkspaceView(view);
  setWorkspaceOpen(true);
};
```

**还要加两处解锁**（否则用户会永远卡在历史视图里）：

1. 新分析跑完时自动回到最新。找到 `setDirectRunResult(...)` 成功赋值的地方
   （直跑完成回调）以及 `handleSelect`（`ProModeView.tsx:217`），各加一行
   `setSelectedRunId(null);`。`handleSelect` 里已经在重置一堆 direct-run 状态，

## 6. ❌ 删除会话失败无任何用户反馈（🟢 建议先做，最简单）

### 症状

侧栏删除一个会话，如果后端返回错误（离线、409、会话被锁），
界面**什么都不显示**，用户以为删成功了，刷新后会话还在。

### 根因

`web/src/AppShell.tsx:98-115`：

```tsx
const handleDeleteSession = useCallback(
  async (sid: string) => {
    if (deletingSessionIds.current.has(sid)) return;
    deletingSessionIds.current.add(sid);
    try {
      await deleteSession(sid);
      if (sid === controller.sessionId) await controller.startNewSession();
      await sessionList.refresh();
    } finally {                              // ← 只有 finally，没有 catch
      deletingSessionIds.current.delete(sid);
    }
  },
  [controller, sessionList],
);
```

`try/finally` 没有 `catch`：异常穿透到 React 事件边界，被静默吞掉。

### 精确改法

**这个项目已有明确惯例，照抄即可**（`AppShell.tsx:136` + `:382`）：
局部 `useState<string | null>` 存文案，用 antd `Alert` + `role="alert"` 渲染。

**Step 1** — 在 `AppShell` 组件内加状态（放在 `deletingSessionIds` 附近）：

```tsx
const [deleteError, setDeleteError] = useState<string | null>(null);
```

**Step 2** — 改 `handleDeleteSession`：

```tsx
const handleDeleteSession = useCallback(
  async (sid: string) => {
    if (deletingSessionIds.current.has(sid)) return;
    deletingSessionIds.current.add(sid);
    setDeleteError(null);
    try {
      await deleteSession(sid);
      if (sid === controller.sessionId) {
        await controller.startNewSession();
      }
      await sessionList.refresh();
    } catch (err) {
      // 过去这里没有 catch，删除失败被静默吞掉，用户会以为已删除。
      // 文案取值顺序与 handleLlmSubmit 一致（ApiError 的结构化 message 优先）。
      setDeleteError(
        err instanceof ApiError ? err.payload.message
          : err instanceof Error ? err.message
            : '删除会话失败，请稍后重试',
      );
      // 失败后强制与服务端对账，避免侧栏停留在「以为已删除」的乐观状态。
      await sessionList.refresh().catch(() => { /* 刷新失败不掩盖原始错误 */ });
    } finally {
      deletingSessionIds.current.delete(sid);
    }
  },
  [controller, sessionList],
);
```

> `ApiError` 已在 `AppShell.tsx:33` 导入，不用加 import。

**Step 3** — 渲染。找到会话抽屉/侧栏里列出会话的地方（`Drawer` 内，
搜 `sessionList` 的渲染位置），在列表**上方**加：

```tsx
{deleteError ? (
  <Alert
    type="error"
    showIcon
    role="alert"
    closable
    onClose={() => setDeleteError(null)}
    message={<span style={{ color: '#cf1322', fontSize: 13 }}>{deleteError}</span>}
  />
) : null}
```

### 验收标准（第 6 项）

| 编号 | 验收点 | 判定方式 | 通过条件 |
|------|--------|----------|----------|
| 6-A | 失败时出现可读错误 | 单测：mock `deleteSession` reject | `role="alert"` 节点可见且含后端 message |
| 6-B | ApiError 用结构化文案 | 单测：reject `new ApiError(...)` | 显示 `err.payload.message`，不是 `[object Object]` |
| 6-C | 非 Error 值有兜底 | 单测：`reject('boom')` | 显示「删除会话失败，请稍后重试」 |
| 6-D | 并发锁仍释放 | 单测：失败后再点一次 | 第二次仍能发起请求（`finally` 生效） |
| 6-E | 列表与服务端对账 | 单测：断言失败后 `refresh` 被调用 | `sessionList.refresh` 调用次数 ≥ 1 |
| 6-F | 成功路径无回归 | 单测 | 成功时不出现 alert |
| 6-G | 用户可关闭提示 | 真机 | 点 × 后提示消失 |

新建 `web/src/__tests__/AppShell.test.tsx`（若已有则追加）。
**注意**：`AppShell` 依赖 5 个 hook + 若干网络调用，直接 render 需要

## 附录 B：为什么有些「显而易见」的改法是错的

留几条踩坑记录，避免接手的人走回头路：

1. **不要让 `skillToAlgorithm('power')` 返回 `'power'`。**
   它的返回值是「Output-Level 算法 id」，要出现在覆盖矩阵里。
   加了会让 sidecar 去找不存在的 power 模板、让
   `tests/property/skill-algorithm-map.property.test.ts` 的不变量崩掉。
   身份字段该在 `research-workflow` 补，那里才知道 dataset_id 和审批链。

2. **不要给功效分析伪造 `dataset_sha256`。**
   它真的没读数据。填一个假指纹会让审计快照的可复现性声明变成谎言。
   前端应该显示「未使用数据集」，而不是想办法凑一个指纹出来。

3. **不要在 `pearsonR()` 里抛错。**
   它是公开导出的裸数值原语，parity 测试当 `cor()` 等价物直接调用。
   拒绝策略属于 `pearsonCorrelation` / `spearmanCorrelation` 那一层
   （已在代码注释里写明）。

4. **Spearman 的零方差判据必须落在原始输入上，不是秩上。**
   常量列的秩也是常量（全部并列在平均秩），在秩上判会漏或晚。

5. **不要用 `payload.method` 当渲染分派判据。**
   那是引擎的展示名（实测 `'One-way ANOVA'`），随文案可变。
   用 `analysis.algorithm_id`（契约）。功效分析例外——它没有 algorithm_id，
   只能靠 `required_n` 这种独有字段判形状。

6. **不要把「正在看历史运行」做成 warning 色。**
   看历史是合法操作，不是故障。用 info。
